# YDB → PostgreSQL

Инструмент для выгрузки YDB и подготовки SQL для PostgreSQL. Работает из командной строки без ИИ. Для запуска через Codex рядом находится скилл с теми же инструментами.

Одна команда создаёт два ZIP: исходный дамп YDB и его конверсию для PostgreSQL. В комплекте есть полностью выдуманная учебная база из четырёх таблиц и 17 строк.

## Проверено на практике

Инструмент успешно использовался на реальных проектах: проверен полный цикл выгрузки YDB, конвертации данных и импорта в PostgreSQL, включая загрузку через pgAdmin Query Tool. Проверенная комбинация CLI — **YDB CLI 2.33 и YC CLI 1.40.0**.

Автоматические локальные проверки дополняют практический опыт: 13 тестов проверяют конвертацию, архивы, большие поля, NULL, ошибки доступа и имена индексов. Учебный пример собирается локально из полностью выдуманных данных.

## Применимость

Перед подключением к рабочей базе проверьте её особенности:

- Поддерживаются обычные строковые таблицы с простыми именами без вложенных путей.
- Типы: UTF8, UINT32, INT32, INT64, BOOL, JSON, JSON_DOCUMENT, DATETIME, TIMESTAMP и Optional этих типов.
- Другие типы, TTL, CDC и специальные индексы требуют отдельного проектирования.
- Режим `--avoid-copy` не гарантирует общего согласованного момента всех таблиц. Для согласованного снимка нужен другой механизм выгрузки.

## Быстрый старт без доступа к облаку

Скачайте репозиторий через **Code → Download ZIP** и распакуйте его либо склонируйте:

```bash
git clone https://github.com/introvert-bz/ydb-to-postgres.git
cd ydb-to-postgres
```

Откройте терминал в корне распакованного или склонированного репозитория. Нужен Python 3.9+; сторонние Python-библиотеки не требуются.

```bash
python3 ydb_to_postgres.py demo --output ./work/shop-example
```

Команда работает локально без облачных учётных данных. Структура результата:

```text
work/shop-example/
  shop-demo-ydb-original.zip
  shop-demo-postgresql.zip
  SHA256SUMS
  shop-demo/
    native-dump/
    jsonl/
    postgres/
    ... метаданные и отчёты
```

Для пробной загрузки создайте отдельную пустую базу PostgreSQL, затем выполните из корня репозитория:

```bash
psql -X --dbname=TARGET_DATABASE --set=ON_ERROR_STOP=1 --file=work/shop-example/shop-demo/postgres/load.sql
psql -X --dbname=TARGET_DATABASE --set=ON_ERROR_STOP=1 --file=work/shop-example/shop-demo/postgres/verify.sql
```

Для pgAdmin используйте SQL в `work/shop-example/shop-demo/postgres/pgadmin/` в порядке, описанном в разделе [загрузки в PostgreSQL](#загрузка-в-postgresql).

## Выгрузка настоящей YDB

### Подготовка подключения

1. Установите [YDB CLI](https://ydb.tech/docs/ru/reference/ydb-cli/install) и [Yandex Cloud CLI](https://yandex.cloud/ru/docs/cli/quickstart) по официальным инструкциям. После установки откройте новое окно терминала.
2. Проверьте доступность команд и версии:

   ```bash
   python3 --version
   ydb version
   yc version
   ```

   В проектах проверены YDB CLI 2.33 и YC CLI 1.40.0. С другой версией сравните доступные параметры через `--help`.
3. Если профиль YC ещё не настроен, выполните `yc init` и пройдите вход под аккаунтом, которому доступна база. Для корпоративного аккаунта следуйте варианту входа из официальной инструкции вашей организации.
4. Посмотрите [список профилей](https://yandex.cloud/ru/docs/cli/operations/profile/profile-list) командой `yc config profile list`. Для `--profile` используется имя **профиля YC**, а не профиль YDB CLI.
5. В консоли Yandex Cloud выберите нужный каталог и базу Managed Service for YDB. Откройте параметры подключения: [официальная инструкция](https://yandex.cloud/ru/docs/ydb/operations/connection). Скопируйте полный путь базы и endpoint из команды подключения.

| Параметр | Что подставить |
| --- | --- |
| `--database` | Полный путь после `-d` в команде подключения, например `/region/cloud/database-id`; не только ID базы |
| `--endpoint` | Адрес после `-e`, включая `grpcs://` и порт, например `grpcs://your-endpoint:2135` |
| `--profile` | Имя существующего профиля YC из `yc config profile list` |
| `--output` | Новую локальную папку результата |

Аккаунту нужны права чтения схемы и строк базы. Точный набор прав согласуйте с администратором базы. Endpoint берите из параметров подключения, а не составляйте из ID.

### Запуск

Подставьте свои параметры:

```bash
python3 ydb_to_postgres.py export \
  --database /region/cloud/database-id \
  --endpoint grpcs://your-endpoint:2135 \
  --profile YOUR_YC_PROFILE \
  --output ./private-backups/export-001
```

Вместо `--profile` можно использовать `--iam-token-file /path/to/iam-token`. Сам токен передавайте файлом. Параметры `--ydb-bin` и `--yc-bin` задают расположение CLI; `--dump-timeout` и `--count-timeout` — время ожидания в секундах.

Результат:

```text
private-backups/
  export-001/                 файлы выгрузки и конвертации
  export-001-ydb-original.zip  исходный дамп YDB
  export-001-postgresql.zip    SQL, отчёты и инструкции PostgreSQL
```

Папка результата и имена архивов должны быть свободны. Исходный архив создаётся перед конвертацией и сохраняется, если преобразование невозможно.

Коды завершения:

| Код | Значение |
| --- | --- |
| 0 | Выгрузка, конвертация и предусмотренные проверки завершены |
| 1 | Ошибка; сохранённые файлы нужно проверить перед использованием |
| 2 | Оба архива созданы, но независимые количества строк источника сверены не полностью |

Справка: `python3 ydb_to_postgres.py export --help`.

Настоящие выгрузки могут содержать клиентские данные и секреты. Папки `private-backups/` и `work/`, логи и файлы токенов исключены через `.gitignore`. Для другого места выгрузки задайте своё исключение или используйте путь вне репозитория.

## Конвертация готового дампа

Команда принимает папку выгрузки этого инструментария:

```bash
python3 ydb_to_postgres.py convert \
  --input ./private-backups/completed-copy \
  --database /region/cloud/database-id
```

Входная папка содержит `native-dump/`, `objects.json`, `*.schema.json`, `database.json`, `download-manifest.json` и `source-counts.json`. Результатов конвертации `jsonl/` и `postgres/` в ней быть не должно; рядом не должно быть одноимённых ZIP.

Если выгрузка завершилась, а конвертация остановилась, используйте сохранённый исходный ZIP. Например, для архива `export-001-ydb-original.zip`:

```bash
mkdir -p ./private-backups/export-002
unzip ./private-backups/export-001-ydb-original.zip -d ./private-backups/export-002
python3 ydb_to_postgres.py convert \
  --input ./private-backups/export-002 \
  --database /region/cloud/database-id
```

`export-002` должна быть новой пустой папкой; рядом не должно быть `export-002-ydb-original.zip` и `export-002-postgresql.zip`. Результаты будут записаны под именем `export-002`. Для следующей попытки выберите другое свободное имя.

Повторный запуск не устраняет неподдерживаемый тип или NULL в ключе: сначала требуется решить указанную причину ошибки. Повторная конвертация из архива не запрашивает данные YDB заново.

## Загрузка в PostgreSQL

Создайте отдельную пустую PostgreSQL-базу и распакуйте архив PostgreSQL. Выберите один способ загрузки.

**psql:** из папки, содержащей `postgres/`, выполните:

```bash
psql -X --dbname=TARGET_DATABASE --set=ON_ERROR_STOP=1 --file=postgres/load.sql
psql -X --dbname=TARGET_DATABASE --set=ON_ERROR_STOP=1 --file=postgres/verify.sql
```

**pgAdmin Query Tool:** выполните `postgres/pgadmin/00_schema.sql`, затем файлы данных по имени, затем `99_verify.sql`. Каждый файл запускайте целиком. Успешно загруженные части повторно не выполняйте. Порядок восстановления после ошибки описан в `postgres/README.txt` внутри архива.

Полный цикл импорта проверен на реальных проектах, включая pgAdmin. Сам скрипт `export` готовит файлы и не подключается к PostgreSQL для загрузки: импорт конкретного архива выполняется отдельно. Поэтому `real_postgres_import_tested: false` в локальном отчёте относится к текущему запуску, а не к истории использования инструмента.

## Учебная база shop_demo

Схема и все строки созданы с нуля для вымышленного магазина. Реальные схемы, клиенты, ключи, ACL и идентификаторы облачных ресурсов не использованы.

| Таблица | Строк | Содержимое |
| --- | ---: | --- |
| customers | 3 | Вымышленные покупатели и адреса в домене `.invalid` |
| products | 4 | Товары, целочисленные цены в минимальных денежных единицах, JSON |
| orders | 4 | Заказы с датами UTC и необязательным примечанием |
| order_items | 6 | Позиции заказов с составным первичным ключом |
| **Всего** | **17** | **4 таблицы** |

Логические связи: `orders.customer_id → customers.id`, `order_items.order_id → orders.id`, `order_items.product_id → products.id`. Данные согласованы по этим связям; внешние ключи в SQL не добавляются.

Пример содержит кириллицу, `+`, апостроф, переносы строк, табуляцию, обратную косую черту, NULL, пустую строку, текст `null`, JSON, BOOL, составной ключ и временные метки UTC с микросекундами.

Готовые файлы:

- [Пример в формате дампа YDB](examples/shop-demo-ydb-original.zip).
- [Конверсия примера для PostgreSQL](examples/shop-demo-postgresql.zip).
- [Контрольные суммы SHA256](examples/SHA256SUMS).

Архив YDB собран локальным генератором в формате входных файлов конвертера. Это учебный пример, а не выгрузка из работающей YDB. Количества строк сверены с генератором; восстановление примера в YDB не тестировалось.

## Проверки и ограничения

Перед упаковкой исходного дампа проверяются список таблиц, наличие схемы и данных, порядок и число колонок, количество строк и отсутствие признаков неполной выгрузки. `download-manifest.json` содержит SHA256 исходных файлов; упаковщик повторно сверяет их. Если входной манифест не содержит `native_files`, проверяются структура и количество строк, а отсутствие сверки исходных хешей явно отмечается в `native_validation`.

Конвертация проверяет значения, диапазоны чисел, NULL и уникальность ключей. Каждое поле PostgreSQL COPY сравнивается с нормализованным JSONL. Для архивов проверяются контрольные суммы и CRC ZIP.

Поддерживаются обычные строковые таблицы с простыми именами и типами UTF8, UINT32, INT32, INT64, BOOL, JSON, JSON_DOCUMENT, DATETIME, TIMESTAMP и Optional этих типов. Остальные типы, вложенные пути, TTL, CDC и специальные индексы требуют отдельного проектирования.

YDB допускает NULL в первичном ключе, а PostgreSQL PRIMARY KEY требует NOT NULL. Если NULL встречается в ключе, конвертация останавливается с именем таблицы и колонки; значения не подменяются. Optional-ключ без NULL переносится как NOT NULL. Исходная и целевая nullable-семантика записаны раздельно в `schema-mapping.json`.

Выгрузка через `--avoid-copy` не гарантирует общего согласованного момента всех таблиц. Отдельный COUNT выполняется после выгрузки и может отличаться из-за изменений в работающей базе. JSONB нормализует JSON. Даты и время преобразуются в TIMESTAMPTZ с UTC. Имена индексов PostgreSQL выбираются без конфликтов с таблицами и первичными ключами; при необходимости имя получает стабильный суффикс. Фактические имена записаны в `schema-mapping.json`.

Запуск 13 локальных тестов и генератора примера:

```bash
python3 ydb-to-postgres/scripts/test_workflow.py
python3 tools/build_examples.py --output ./work/demo-build
```

Для каждого запуска генератора укажите новую папку.

## Диагностика

Ошибка CLI содержит имя этапа без команды, токенов и содержимого ответа:

| Этап или сообщение | Что проверить |
| --- | --- |
| `authentication` | Действительность входа в YC, имя профиля; при истёкшей авторизации повторите разрешённый для вашего аккаунта вход |
| `discovery` | Endpoint, полный путь базы, сетевой доступ и права на просмотр схемы |
| `schema:TABLE` | Права и доступность метаданных конкретной таблицы; ожидаемый формат вывода CLI |
| `dump` | Частный файл `dump.log` внутри папки `--output`; свободное место, доступность YDB и время ожидания |
| `count:TABLE` / `source_verified: false` | Права на чтение строк, таймаут COUNT и изменения данных после выгрузки; итог в `source-counts.json` |
| `Output directory already exists` / `Conversion output exists` | Новую папку результата или повторную конвертацию из исходного ZIP по примеру выше |
| `Unsupported YDB type` / `TTL/CDC` | Применимость сопоставления схемы; исходный архив сохраняется |
| `NULL in YDB primary key` | Отдельную схему переноса ключа: PostgreSQL PRIMARY KEY не допускает NULL |
| `Native files differ from download checksums` | Целостность исходных файлов: не изменяйте их и не снимайте проверку хешей ради продолжения |

Путь лога при `--output ./private-backups/export-001`: `./private-backups/export-001/dump.log`. Лог создаётся на этапе дампа, поэтому при ошибке авторизации или обнаружения таблиц его ещё может не быть. В коде завершения 2 оба архива готовы, но сверка независимых количеств строк неполная.

`dump.log` может содержать чувствительные данные CLI. Просматривайте его локально; перед передачей диагностики удалите секреты. Отключённая или недоступная операция не считается выгрузкой нулевого числа строк.
